## 1. Scope and ownership boundary

The Temporal Notepad is the **current state-semantics owner** and minimal persistent-state substrate.

```text
TEMPORAL NOTEPAD
= CURRENT STATE SEMANTICS OWNER
+ HISTORY / PROVENANCE / STATE CLASSES
+ DETERMINISTIC MUTATION BOUNDARY
+ PASSIVE MUTATION TELEMETRY
+ IDENTITY-BINDING STATE CONSTRAINTS

TEMPORAL NOTEPAD
!= COMPLETE HARNESS / JUDGMENT LAYER / ENVIRONMENTAL REGULATOR / OPERATIONAL POLICY OWNER
```

```text
ENVIRONMENT
→ DAO_ENVIRONMENT_CALIBRATION_HYGIENE
→ OWNS NON-STATE SEMANTICS
   (PURPOSE / ENTRY / EVIDENCE / JUDGMENT / ACTION / STOP / EVOLUTION)
→ REFERENCE APPLICABLE ENVIRONMENT ARTIFACT
↛ DETERMINE ENVIRONMENT CURRENTNESS / VERSION HERE
↛ REIMPLEMENT HERE
```

The Notepad may expose state consumed by those predicates; it does not own them.

```text
CURRENT STATE OWNER
!= PERMANENT OWNER
!= TRUTH AUTHORITY

OWNER
→ BOUNDED TO EXPLICIT STATE SEMANTICS
→ MAY CHANGE WHEN CURRENT EVIDENCE CHANGES THE DISPOSITION
```

## 2. Persistent-state surfaces

```text
CURRENT VIEW
→ smallest sufficient current temporal-state projection
↛ complete source / world / judgment state

SEMANTIC STATE RECORD
→ append-only accepted persisted temporal-state transitions

BOUNDARY EVENT RECORD
→ append-only material mutation-boundary events
→ MAY INCLUDE accepted transitions and material rejected / stale / invalid attempts

SEMANTIC STATE RECORD != BOUNDARY EVENT RECORD
DURABLE RECORD != TRUE CLAIM ABOUT THE WORLD
CURRENT VIEW != COMPLETE WORLD STATE / COMPLETE JUDGMENT STATE
```

`EVENTS.jsonl` remains the named boundary-event record where used; accepted persisted transitions form the semantic-state-record subset.

## 3. State classes

The current-view schema must not collapse state classes that the transition model keeps distinct.

At minimum:

```text
VERIFIED
SUPPORTED
UNKNOWN
UNRESOLVED
CONTRADICTED
INVALIDATED
SUPERSEDED
```

Preserve:

```text
CONTRADICTED
!= INVALIDATED
!= SUPERSEDED
```

`KNOWN` should not be used as a synonym for `JUSTIFIED`.

Classification support uses the applicable Environment evidence semantics; the Notepad stores the resulting state class and provenance rather than defining epistemic policy independently.

## 5. Semantic-state proposal interface

A proposed semantic-state delta may enter only after the Environment-resolved path makes proposal admissible.

```text
ELIGIBLE_FOR_PROPOSAL → MAY SUBMIT PROPOSED DELTA
ELIGIBLE_FOR_PROPOSAL ↛ DUTY_TO_PROPOSE / SEMANTIC-STATE PERSIST / STATE_DELTA RECORD
```

Minimum proposal relations, when applicable:

```text
proposer_ref
[identity_binding_ref]
[executor_ref]
[action_authorization_ref]
[observer_ref]
[source_refs]
```

A concrete writer may additionally require expected semantic-view currentness/version, operation, target, proposed delta, and rationale. Event-tail ancestry / ordering should be required only when load-bearing to the proposed operation.

A verified `identity_binding_ref` is requisite only when identity is load-bearing to the proposed mutation; absence where identity is not load-bearing is not a defect.

```text
FIELD PRESENCE != VERIFIED BINDING
```

## 6. Deterministic mutation boundary

Environment resolves materiality, load-bearing status, applicable authorization / support requirements, and permitted scope. The mutation boundary enforces them; it does not re-judge them.

```text
RECEIVE PROPOSED STATE_DELTA
→ CHECK EXPECTED SEMANTIC-VIEW CURRENTNESS / VERSION WHERE IMPLEMENTED
→ CHECK STATE-LOCAL TRANSITION SEMANTICS
→ CHECK RESOLVED IDENTITY / AUTHORIZATION / SUPPORT / SOURCE REQUIREMENTS WHERE APPLICABLE
→ CHECK RESOLVED TARGET / SCOPE / ROLLBACK DATA WHERE APPLICABLE

RESOLVED REQUIREMENT INPUT
→ BIND TO PROPOSED DELTA / TARGET / PERMITTED SCOPE /
  RELEVANT SEMANTIC-VIEW CURRENTNESS
→ BIND TO RELEVANT EVENT-TAIL ANCESTRY ONLY WHEN LOAD-BEARING
RAW REF / BOOLEAN / LABEL
↛ RESOLVED REQUIREMENT

DETERMINISTIC MUTATION BOUNDARY
→ ENFORCES ALREADY-RESOLVED REQUIREMENTS
↛ RE-JUDGES PURPOSE / NECESSITY / MATERIALITY / EPISTEMIC WEIGHT
```

```text
VALID MATERIAL STATE_DELTA
→ APPEND TRANSITION EVENT
→ UPDATE / REGENERATE CURRENT VIEW

MATERIAL PROPOSAL
+ FAILS A RESOLVED REQUISITE
  CURRENTNESS / STATE-LOCAL VALIDITY / IDENTITY / AUTHORIZATION /
  SUPPORT / SOURCE / TARGET / SCOPE REQUIREMENT
→ REJECT SEMANTIC-STATE MUTATION
→ MAY APPEND PASSIVE TELEMETRY

NO MATERIAL STATE DELTA → NO SEMANTIC STATE MUTATION

MUTATION BOUNDARY ACCEPTANCE
→ CURRENT SEMANTIC STATE MAY CHANGE
!= TRUE CLAIM ABOUT THE WORLD
```

## 7. Identity-binding state constraints

A free-text actor or populated identity field is not a verified binding.

```text
IDENTITY CLAIM != IDENTITY BINDING

IDENTITY CLAIM PRESENT
+ identity_binding_ref POPULATED
+ BINDING NOT VERIFIED
→ REJECT SEMANTIC-STATE IDENTITY MUTATION
→ PRESERVE CLAIM / ATTEMPT AS TELEMETRY WHERE MATERIAL
```

Identity-related proposal relations are those defined in §5.

```text
↛ RE-JUDGE MATERIALITY LOCALLY
```

## 11. Backend boundary

The Notepad state contract does not require a particular persistence backend.

```text
PERSISTENCE BACKEND
!= STATE SEMANTICS
```

A compatible backend needs only the capabilities required by the active state contract, such as:

```text
READ CURRENT VIEW
READ REQUISITE EVENT HISTORY
COMPARE EXPECTED SEMANTIC-VIEW CURRENTNESS / VERSION
APPEND OR DURABLY RECORD EVENT
WRITE / REGENERATE DERIVED CURRENT VIEW
RETURN SEMANTIC-VIEW VERSION / HASH WHERE IMPLEMENTED
RETURN BOUNDARY-EVENT TAIL / CURSOR WHERE IMPLEMENTED
```

```text
SEMANTIC_VIEW_VERSION / HASH
!= BOUNDARY_EVENT_TAIL / CURSOR

SEMANTIC MUTATION
→ BIND TO SEMANTIC-VIEW CURRENTNESS

BOUNDARY-EVENT ANCESTRY / ORDER
→ BIND TO EVENT TAIL ONLY WHEN LOAD-BEARING

DISTINCT TEMPORAL COORDINATES
↛ UNIVERSAL DUAL-VERSION REQUIREMENT

BOUNDARY-EVENT APPEND
+ NO SEMANTIC-STATE MUTATION
→ SEMANTIC_VIEW_VERSION / HASH UNCHANGED
```

```text
CONCURRENT SEMANTIC MUTATION
→ SINGLE-WRITER SERIALIZATION
  OR ATOMIC COMPARE-AND-COMMIT

INTERRUPTED ACCEPTED SEMANTIC TRANSITION
→ DETERMINISTIC RECOVERY TO ONE VALID EVENT / CURRENT-VIEW PAIR

POSSIBLE CONCURRENCY FAILURE
!= ESTABLISHED NEED FOR NEW COORDINATION MACHINERY
```

Backend expansion requires an independently demonstrated load-bearing need through the owning operational semantics.
